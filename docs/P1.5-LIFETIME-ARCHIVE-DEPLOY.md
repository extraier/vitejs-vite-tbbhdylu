# P1.5 Lifetime Archive — Deployment Guide

This is the one-time setup + per-deploy recipe for the lifetime archive
cron + NAS endpoint. Two sides:

1. **Cloud Functions** (us-central1) — runs `dailyArchiveLifetimeEvents`
2. **NAS** — `photo_upload_server.py` exposes `POST /archive`

Both must agree on the HMAC secret. The README explains.

## Pre-flight: one-time setup

### 1. Pick the HMAC secret

The archive endpoint uses the same `PHOTO_HMAC_SECRET` already
configured on the NAS. Confirm both sides have it:

```bash
# On the NAS
ssh openclaw@nas
cat /home/openclaw/.config/photo-upload/server_secret
# copy the value
```

### 2. Wire the CF secret

The CF reads `NAS_ARCHIVE_HMAC_SECRET`. The value MUST equal the
NAS secret. Without this, the CF mints tokens the NAS rejects,
and every archive request fails with `unauthorized (token mismatch)`.

```bash
firebase functions:secrets:set NAS_ARCHIVE_HMAC_SECRET
# paste the exact value from step 1
```

Then grant the function access:

```bash
gcloud functions add-invoker-policy-binding \
  dailyArchiveLifetimeEvents \
  --region=us-central1 \
  --member="serviceAccount:savetheday-2377a@appspot.gserviceaccount.com"
```

(The default service account can read the secret; the binding is
just to confirm.)

### 3. Deploy the Firestore index

The cron queries `events` with `retentionClass=lifetime AND archivedAt=null`.
That's a composite equality on two fields — Firestore needs an explicit
index. The `firestore.indexes.json` already has it (added with P1.5),
but Composite indexes are deployed separately:

```bash
firebase deploy --only firestore:indexes
```

Takes ~2-5 minutes. Without it, the first cron tick will fail with
`FAILED_PRECONDITION: The query requires an index` and no events
will be archived.

cd /Users/roger/projects/vitejs-vite-tbbhdylu
export CLOUDSDK_PYTHON=/opt/homebrew/bin/python3.14
./scripts/deploy-functions.sh dailyArchiveLifetimeEvents

### Ship the NAS endpoint

The existing `ship-feature.sh` already rsyncs
`deploy/photo_upload_server.py` to the NAS and restarts it via
`ts-autostart.sh`. The new `POST /archive` endpoint is part of the
same file, so no new deploy step:

```bash
./scripts/ship-feature.sh
```

### Verify the NAS endpoint is reachable

```bash
curl -sS -X POST https://cdn.savetheday.io/archive \
  -H "Content-Type: application/json" \
  -d '{"eventId":"test","ownerUid":"test"}'
# expected: 401 missing X-Archive-Token (or 404 if the route is missing)
```

If you get **404**, the new endpoint hasn't been picked up by the
NAS — the `ts-autostart.sh` may not have restarted the server. Run:

```bash
ssh openclaw@nas pkill -f photo_upload_server.py
ssh openclaw@nas /home/openclaw/bin/ts-autostart.sh
```

## Smoke test the cron manually

Before the first cron tick, manually trigger one archive to verify
the wiring works end-to-end:

1. Set up a test event in Firestore:
   - `events/{ownerUid}/events/{eventId}` with `retentionClass: "lifetime"`, `date: "2026-01-01"`, `archivedAt: null`
   - Add a few photos directly to `/volume1/flight-scanner/wedding-photos/{eventId}/`

2. In the Firebase Console: Functions → `dailyArchiveLifetimeEvents` → "Run now".

3. Check the logs:
   - Cloud Functions logs: should show `[dailyArchiveLifetimeEvents] archived {eventId} filesCopied=N`
   - NAS logs: should show `archived {eventId}` from `photo_upload_server.py`
   - `/volume1/flight-scanner/wedding-photos-archive/{eventId}/` should now exist
   - `/volume1/flight-scanner/wedding-photos-archive-log/{eventId}.json` should be written

4. Verify photo retrieval still works:
   - Open a browser to one of the photos via the public URL
   - Server should still serve it (from primary)

5. Verify archived retrieval works:
   - Delete the photo from primary
   - Open the same URL in the browser
   - Server should serve it from archive (Q3: direct serve)

## Schedule

The cron runs daily at **03:15 HKT** (`15 3 * * *`, Asia/Hong_Kong).
The 30-day buffer means events are archived 30 days after the
`event.date` is in the past.

To test the cron in staging/dev, override:

```bash
ARCHIVE_POST_WEDDING_DAYS=0 firebase functions:secrets:set ARCHIVE_POST_WEDDING_DAYS
```

(No, scratch that — `POST_WEDDING_DAYS` is a module-level constant,
not a secret. Re-deploy the function with the env var set on the
CF runtime to override for that deployment.)

## Troubleshooting

### "unauthorized (token mismatch)" on every request

CF secret ≠ NAS secret. Check both:

```bash
firebase functions:secrets:access NAS_ARCHIVE_HMAC_SECRET
# on the NAS
ssh openclaw@nas cat /home/openclaw/.config/photo-upload/server_secret
```

### "FAILED_PRECONDITION: The query requires an index"

Index not deployed. Run `firebase deploy --only firestore:indexes`.

### "free disk NN < ARCHIVE_MIN_FREE_BYTES"

The NAS is below the 5 GB reserved threshold. Either free up space
or temporarily override:

```bash
# on the NAS
export PHOTO_ARCHIVE_MIN_FREE_BYTES=1073741824  # 1 GB
# restart the photo server
```

### Photos are not appearing from archive

Check:

```bash
ls /volume1/flight-scanner/wedding-photos-archive/{eventId}/
ls /volume1/flight-scanner/wedding-photos-archive-log/{eventId}.json
```

If the manifest exists but the files don't, the archive copy failed
mid-way. Re-run the cron — the per-file sha256 resume will pick up
where it left off.

## Rollback

If something goes wrong, you can pause the cron by deleting the
scheduled job:

```bash
gcloud scheduler jobs delete firebase-schedule-dailyArchiveLifetimeEvents \
  --location=us-central1
```

The NAS endpoint stays open but no calls will come in. To fully
revert, deploy the previous `photo_upload_server.py`:

```bash
# on the NAS
ssh openclaw@nas
cp /home/openclaw/bin/photo_upload_server.py /home/openclaw/bin/photo_upload_server.py.bak
# restore via your backup method
```
