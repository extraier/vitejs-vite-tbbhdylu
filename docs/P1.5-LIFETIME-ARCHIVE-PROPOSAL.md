# P1.5 — Lifetime archive job: design proposal

**Status:** awaiting product decision before code work begins.
**Author:** Manus (drafted 2026-08-19 after shipping P1.4.a).

---

## What "lifetime archive" means today

The unlock `permanent-archive` already exists in `UNLOCK_PRICING`
(`functions/src/unlocks.ts:48`) and is honored by
`computeEntitlement()` (`functions/src/entitlementResolver.ts:196`).
It sets:

```ts
features.lifetimeRetention = true;
retentionClass = 'lifetime';
```

…which the client receives from `getEventEntitlement` but **does not
yet act on**. No code currently moves files anywhere when an event
flips to lifetime. Customers who buy permanent-archive get the badge
in their dashboard but no actual storage guarantee.

---

## What needs deciding

### Question 1 — Where is "archive"?

The current photo storage is on a UGREEN NAS at
`/volume1/flight-scanner/wedding-photos` (single tier, no cold/archival
storage configured). Options:

| Option | Effort | Cost | Customer promise |
|---|---|---|---|
| **A. Same-NAS copy** — duplicate `eventId/` to `/volume1/wedding-photos-archive/` with a manifest, keep both paths live | small (~1 dev day) | 2× disk (acceptable at scale) | Files survive even if primary path is corrupted; no offsite protection |
| **B. Cold tier** — add a second NAS volume or external B2/Glacier mount, copy on schedule | medium (~3 dev days) | ½–⅓ of primary cost (cheap cold storage) | Real archival guarantee; recovery procedure needed |
| **C. No copy** — store `retentionClass='lifetime'` as metadata only, with a policy doc that the NAS itself is the archival | trivial (~1 hour) | zero | Implicit promise that the NAS doesn't die; no programmatic enforcement |
| **D. Compress-and-stay** — keep one copy, but recompress primary photos to a more compact codec (e.g. webp from jpeg) for events older than 6 months, freeing primary space | medium (~3 dev days, codec conversion is non-trivial) | lower | Storage savings; no archival guarantee |

### Question 2 — When does archival happen?

| Trigger | Pros | Cons |
|---|---|---|
| **On unlock purchase** — copy immediately when the customer pays for permanent-archive | simple, no scheduler; customer sees instant guarantee | customer pays for a single download that's already in primary; copy can fail and leave no record |
| **Daily cron, 30 days post-wedding-date** — schedule runs once a day, copies events whose `date < today − 30d && retentionClass == 'lifetime'` | standard archival pattern; idempotent; logs every move | requires a scheduler (Cloud Scheduler + CF cron); adds latency to when "lifetime" actually becomes effective |

### Question 3 — What about retrieval?

If a customer requests a download of a photo from an archived event
6 years later, does the NAS serve it directly, or do we restore the
copy first?

- **A. Direct serve** — keep both paths mounted by the photo server, look up by `eventId` in both
- **B. Restore-on-demand** — return a 202 + job id, restore in background (~5 min), notify the customer

---

## Recommendation

For a wedding SaaS at current scale, **Option A + 30-day-post-wedding cron**:

- 1 dev day to implement
- Zero new infrastructure (same NAS, just a second folder)
- Idempotent (re-running the cron on already-archived events is a no-op)
- The "lifetime" promise becomes real — files survive primary-path corruption
- Re-evaluate when storage exceeds 50% of NAS capacity

For each event archived:
1. Copy `eventId/` directory to `…/wedding-photos-archive/eventId/`
2. Write a manifest record: `archive_log/{eventId}.json` with timestamp, file count, total bytes, sha256 of each file
3. Set `event.archivedAt = Date.now()` so the cron skips it next time
4. No special retrieval logic needed — keep both paths served

Implementation would touch:
- `functions/src/cron/archiveJob.ts` (new, ~80 lines)
- `functions/src/index.ts` (export)
- Cloud Scheduler trigger (1 line in firebase.json or via gcloud)
- Tests: ~10 cases (idempotency, partial-copy recovery, quota gate so it doesn't OOM)

---

## Out of scope

- Real cloud cold tier (B2/Glacier) — add when NAS exceeds 50%
- Restoration UI — the photo server already serves from any path
- Per-customer archival status display — `event.archivedAt` is
  queryable from the existing dashboard
