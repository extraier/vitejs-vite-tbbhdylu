# P1.5 lifetime archive — questions for Roger

The unlock `permanent-archive` is already plumbed end-to-end (price set,
entitlement flips, `retentionClass='lifetime'` returned to the client).
But no code actually moves files when an event is lifetime. These 3
questions unblock the rest.

Reply with your picks (e.g. "Q1=A, Q2=B, Q3=A") and I'll build it.

## Q1 — Where do archive copies live?

| Option | Cost | Effort | What it gives you |
|---|---|---|---|
| **A. Same-NAS duplicate folder** `…/wedding-photos-archive/eventId/` | 2× disk | ~1 dev day | Files survive primary-path corruption only. No offsite. |
| **B. Cold tier** (B2 / S3 Glacier / second NAS volume) | ~⅓ primary | ~3 dev days | Real cold-tier guarantee. Needs restore path. |
| **C. Metadata-only** (no copy) | 0 | ~1 hour | Documented promise only. No enforcement. |
| **D. Compress in place** (jpeg→webp for >6mo events) | saves space | ~3 dev days | No archival guarantee. |

**Recommended default if you defer:** A. Smallest lift, real archival
guarantee on the same hardware, no new infra. Re-evaluate when NAS >50%.

## Q2 — When does the archive job run?

| Trigger | Pros | Cons |
|---|---|---|
| **A. On unlock purchase** (CF fires immediately on `permanent-archive` approval) | Instant guarantee; no scheduler | Fails silently if NAS is down; triggers on events that haven't happened yet |
| **B. Daily cron, 30 days post-wedding-date** | Standard archival pattern; idempotent; logs every move | Requires Cloud Scheduler; "lifetime" becomes effective at T+30d |

**Recommended default:** B. Combined with `event.archivedAt` as a
skip-flag, the cron is idempotent (re-runs are no-ops). The 30-day
buffer handles weddings that get rescheduled.

## Q3 — How does the customer view/retrieve an archived event?

| Option | Effort | UX |
|---|---|---|
| **A. Direct serve** (photo server reads both paths) | Small | Instant. Photo grid looks the same. |
| **B. Restore-on-demand** (202 + job id, restore in ~5min, notify) | Medium | Customer waits. Needs a "restoring…" state. |

**Recommended default:** A. The photo server already serves from any
path; the lookup just needs to check both `/wedding-photos/` AND
`/wedding-photos-archive/`. No UX change.

## What I'll build once you pick

Whichever combo you pick, the implementation is:

1. **`functions/src/cron/archiveJob.ts`** — new CF scheduled function
   (`onSchedule('every day 03:00')`). Queries events where
   `date < today − 30d AND retentionClass == 'lifetime' AND archivedAt == null`.
   For each: copies `eventId/` directory to archive path, writes
   manifest, sets `event.archivedAt = Date.now()`.

2. **`functions/src/cron/listArchivedEvent.ts`** — tiny helper
   functions to find the photo path (primary or archive) given
   `eventId`. Used by the photo server on retrieval.

3. **`api/photo-upload.js`** — on photo retrieval, if the event is
   archived, append the archive path to the LOOKUP set. No new write
   path.

4. **Tests** — 10 cases:
   - Idempotency (re-run on archived event is a no-op)
   - Partial-copy recovery (resume from last successful file)
   - No-op when no events match the filter
   - Manifest contains sha256 of each file
   - Quota gate (don't copy if event bytes > NAS free space)
   - Skip event with `archivedAt` already set
   - Skip event whose `date` is in the future
   - Skip event whose `retentionClass` is 'standard'
   - Archived event's photo retrieval serves from archive path
   - Unarchived event's photo retrieval still serves from primary

5. **Cloud Scheduler trigger** — `firebase.json` pubsub trigger

6. **Migration** — none required. Existing customers who already
   bought `permanent-archive` will get their events archived on the
   first cron tick after the wedding-date passes the 30-day threshold.
